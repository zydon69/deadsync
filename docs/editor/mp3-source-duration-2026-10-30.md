# MP3 source duration: decoded EOF versus FMOD allocation

## Explicit source correction

Keep the native editor's 8,064 decoded frames for the short Info fixture. Do not expand it to FMOD `MODE.DEFAULT`'s 17,280-frame allocation. The additional 9,216 frames are all zero, after an exactly identical 8,064-frame decoded prefix. This is a documented correction of source allocation overestimation, not a claim to reproduce that empty allocation as music.

Do not trim to the last nonzero frame either: the native 8,064 frames retain 1,104 decoded silent frames after frame 6,959. Encoded silence and the source's Info lead remain valid timeline data. Switching to gapless 4,725 frames would change that source timeline and is not this correction.

## Actual API measurements

Pinned Fumen `0fe292f9c0ef70fb77d61cb54316a7e78dbf3c89`, actual bundled FMOD macOS library, `NOSOUND_NRT` (no physical output). Original Fumen `SoundManager.FillSamples` obtains `getLength(PCMBYTES)`, locks that allocation, and parses its full length. Diagnostic comparisons call the actual FMOD APIs:

| Fixture / API | Declared PCM frames | Locked or read frames |
|---|---:|---:|
| Short / original `MODE.DEFAULT`+`getLength`+`lock` |17,280|17,280|
| Short / diagnostic `ACCURATETIME`+`lock` |8,064|8,064|
| Short / diagnostic `OPENONLY`+`readData` until `ERR_FILE_EOF` |17,280|8,064|
| Short / diagnostic `OPENONLY\|ACCURATETIME`+`readData` |8,064|8,064|
| Existing timeline.mp3 / `MODE.DEFAULT`+`lock` |109,440|109,440|
| Existing timeline.mp3 / `ACCURATETIME`+`lock` |108,288|108,288|
| Existing timeline.mp3 / `OPENONLY`+`readData` EOF |109,440|108,288|

For both files, accurate lock and both EOF reads are byte-identical. DEFAULT's prefix is byte-identical to them; its surplus is entirely zero (9,216 short frames;1,152 existing-timeline frames). `readData` consumes the actual decoder to EOF, so this distinction does not infer duration from nonzero amplitudes.

The editor's frame counts, metadata and prepared-source counts already match actual EOF. No production decoder change is needed. The separate regression test fixes this contract in place.

These duration measurements do not establish codec-bit equality: versus actual FMOD EOF PCM16, native Symphonia differs on 4,961 samples in the short fixture (maximum absolute integer delta 810) and 32,149 samples in the existing timeline fixture (maximum delta 1). These are reported differences, not accepted PCM tolerances. Both files' first/last nonzero positions agree between source and native, but no general codec parity follows.

## Fixture and reproduction

Checked-in short fixture: `crates/deadlib-audio-decode/tests/fixtures/editor-source-short-info.mp3` (2,760 bytes), SHA256 `5d4ae4e0e6d1979149577c730b7b55f0f8b4658ed43d04daf78afb2e4e07d7d0`.

Generated and regenerated byte-identically with FFmpeg 8.1.1:

```sh
ffmpeg -y -v error -i assets/sounds/editor_beat_tick.wav -c:a libmp3lame editor-source-short-info.mp3
```

Input WAV SHA256 `274e42d73c61706dff1342410fc2129653e9d5782d805c58380594489383f473` (stereo 44,100 Hz, 4,725 frames). FFprobe observes six audio MPEG frames plus the separate Info frame: source/editor timeline is 7×1,152=8,064, not the 4,725 gapless frames.

`scripts/editor_mp3_fmod_duration_reference.py` runs the four actual FMOD modes, records binary/fixture provenance, compares raw PCM byte-for-byte and requires the DEFAULT surplus to be all zero. It never uses a nonzero-frame trimming heuristic. The test fixture is checked in, so native tests require neither FMOD nor FFmpeg.
